# Сквозные проверки smoke (§6.1)

`run.sh` гонит сценарии подряд в порядке таблицы и выходит с кодом 1 на первом сбое: строка
«S<n>: <причина>», за ней хвост вывода сценария (файл — в `.smoke/` корня копии). Итог —
«сценариев N из M»; ноль засчитанных — красное. Пропуск — только по имени и с причиной:
`run.sh --skip 'S2=<причина>'`, итог его называет. Второй `run.sh` в той же копии выходит с кодом 1
«smoke уже идёт в этой копии»; остатки прошлого прогона (группу сервера и базу smoke) следующий
прогон снимает первыми и говорит об этом строкой.

| ID | Command | Expected | Timeout |
|---|---|---|---|
| S3 | пустая база smoke своего корня → `alembic upgrade head` из `backend/` | код 0; ревизия базы — head цепочки; все таблицы `models.Base.metadata` есть в `public` | 120 с |
| S1 | на базе S3 `python -m ai_geo_audit.api`, затем `python -m ai_geo_audit.api.probe` | проба — код 0 не позже 15 с после старта; по `SIGTERM` — конец сигналом `SIGTERM` не позже 25 с | 60 с |
| S2 | `uv run --no-sync pytest` из `backend/` | код 0, «пропущено 0» | 600 с |

Чего S1 не доказывает: доступности из сети стека — её судит оракул стека (джоба `stack`); боевого
старта (`APP_ENV=prod`, проверка старта с секретами) — S1 идёт на `dev`, как живой тест A55.

Окружение до сценариев: интерпретатор `backend/.venv`, пакет `ai_geo_audit` из `backend/src` этой
копии, Postgres тестов (`docker compose -f docker-compose.dev.yml up -d db`). Не так — строка
«окружение: …» или «судится чужой пакет: <путь>», код 1, ни один сценарий не засчитан.
