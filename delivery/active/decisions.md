# Decisions

Срез 0 — числа боевого наложения и запас порога `stop-grace`; строк кода нет.

- 2026-11-24 · выбрал `mem_limit` и `cpus` по замеру своего стека с запасом вместо чисел соседа
  (З80: api 1g и 2.0, web 256m и 0.5, база 4g и 2.0), потому что наш стек на шагах оракула
  берёт десятки мебибайт. Замер — `docker stats` стека оракула 2026-11-24T10:26:59–10:29:44Z
  (25 шагов, красных 0; Docker 29.9.3 на машине, 10 CPU, aarch64), пик: api 71,6 МиБ и 36,3 %
  ядра, db 24,6 МиБ и 6,5 %, redis 15,6 МиБ и 6,0 %, web 10,7 МиБ и 4,2 %. migrate короче такта
  замера, его пик — проба импорта в образе: 62,7 МиБ. Числа: api — 512m и 1.0, один процесс
  uvicorn (`workers: 1`); migrate — 256m и 1.0; db — 1g и 1.0 (буферы и соединения — строка о
  `max_connections`); redis — 256m и 0.5; web — 128m и 0.5: nginx держит процесс на ядро, на
  машине с 10 CPU их 11. Цена — оценка, а не замер под нагрузкой: тесный лимит убьёт процесс по
  памяти (код 137), пересчёт — этап 1.1, конец Части 5; сумма лимитов — 2176 МиБ и 4 ядра.
- 2026-11-24 · выбрал `--maxmemory 100mb` при `mem_limit` 256m вместо доли соседа (384mb при
  512m, 75 %), потому что Redis 7.4 по умолчанию пишет снимки — `save 3600 1 300 100 60 10000`
  в каталог `/data`, том образа (проба 2026-11-24), — а снимок пишет дочерний процесс: страницы,
  изменённые за время снимка, копируются, и в худшем случае память почти удваивается (вывод, не
  замер). При 75 % в худшем случае лимит убил бы Redis (код 137) вместо явного отказа записи —
  тоже вывод. Пик на шагах оракула — 15,6 МиБ. `--maxmemory-policy noeviction` — явной строкой,
  хотя это и умолчание 7.4 (та же проба): правило `redis-memory` судит команду, а не умолчание
  версии. Цена — очередь больше 100 МБ получает отказ записи; пересчёт — этап 1.1.
- 2026-11-24 · выбрал `max_connections` 50 вместо умолчания Postgres 16 (100) и 150 у соседа,
  потому что лимит db 1g должен держать худший случай, а одновременно соединений сейчас нужно не
  меньше 12: пул api — 5 и 5 сверху; движок здоровья api — без пула, новое соединение на каждую
  проверку (`build_engine("health")` в `api/health.py`): Docker проверяет раз в 10 с, ещё —
  оракул и будущий сторож Ч1.14; migrate — 1 без пула, при выкате он работает, пока жив старый
  api. Проба 2026-11-24 на образе db: 40 соединений добавили 54,9 МиБ — 1,4 МиБ на соединение в
  простое; буферы — 128 МБ, `work_mem` — 4 МБ на сортировку, запас суперпользователя — 3
  (умолчания 16, та же проба). 50 соединений с сортировкой у каждого — около 400 МБ (счёт по
  пробе), в 1g с запасом. Цена — правило `db-connections` Части 3 считает и пулы, и движки без
  пула: их сумма должна уложиться в 47, а смена числа пересоздаёт контейнер базы.
- 2026-11-24 · выбрал метку журнала `tag` с именем сервиса — `ai-geo-audit-api`,
  `ai-geo-audit-db` и так у каждого из пяти — вместо умолчания драйвера и шаблона `{{.Name}}`,
  потому что `tag` задаёт `CONTAINER_TAG` и `SYSLOG_IDENTIFIER` (документация Docker, драйвер
  journald, чтение 2026-11-24), а умолчание — первые 12 знаков ID контейнера: ID меняется при
  каждом пересоздании, и журнал сервиса до и после выката не собрать одним `journalctl -t`;
  `{{.Name}}` — имя контейнера с именем проекта и номером реплики, и правило `journald` не
  увидит в нём имя сервиса. Цена — у двух стеков этого сервиса на одной машине метка общая:
  различит их `CONTAINER_NAME`, его драйвер пишет всегда.
- 2026-11-24 · выбрал запас 10 с к пределу uvicorn в пороге `stop-grace` у api (порог 30 с)
  вместо порога «больше предела uvicorn», потому что после мягкой остановки api ещё закрывает
  пул базы (`_lifespan` → `dispose_engine()`), а своего предела закрытия пулов в коде нет —
  `await engine.dispose()` без `wait_for`, — поэтому 10 с — оценка, не замер (решение
  проверяющего 2026-11-24). Цена — `stop_grace_period` 25 с краснеет, хотя мягкая остановка
  uvicorn укладывается в 20 с.
- 2026-11-24 · выбрал продолжить по плану при мере 855 строк с кодом среза 3 (670 до его коммита,
  порог стопа 650) вместо остановки и перепланирования, потому что прогноз до конца — около
  1150–1200 строк, ниже порога «сказать до сдачи» 2300 и предела 2500 (решение ведущей
  2026-11-24). Оценка плана — 436 (×2), а тяжелее оценки тесты: проба на каждое условие (L53) и
  тест на каждую ветку функций шага (L88); из 855 код — около 277 строк, тесты — около 578. Цена —
  поставка почти втрое больше оценки; новый стоп — перед коммитом кода среза 4 и дальше, если
  прогноз выше 1200 (позже ведущая подняла порог до 1500 — строка ниже); в отчёт сдачи — урок о
  множителе для поставок с правилами и шагами оракула.
- 2026-11-24 · выбрал коммит кода среза 4 при прогнозе около 1230 строк вместо стопа на пороге
  1200, потому что превышение — 2,5 %, далеко ниже 2300 и 2500 (решение ведущей 2026-11-24, после
  слияния main `5560a6a`: мера против main — 925). Цена — порог стопа поднят до 1500; мера с кодом
  среза 4 — 1334, прогноз до конца со срезом 5 и добивками — около 1390.
- 2026-11-24 · выбрал в правиле `limits` судить наличие `mem_limit` и `cpus` (пусто и ноль — тоже
  «нет») вместо сравнения чисел в байтах из строки рисков плана, потому что в выводе
  `--no-interpolate` compose 5.7.0 значения стоят как в файле: `mem_limit` — `1g`, `256m`,
  `512M`, `cpus` — число или строка, а `command` строкой не делится на слова; байты и разбитая
  команда — только в выводе с подстановкой (проба 2026-11-24T11:18Z). Пример A89 требует наличия,
  а не величины. Цена — правило не ловит слишком большой лимит; команду Redis строкой правило
  делит само (`shlex`), списком — берёт как есть.
