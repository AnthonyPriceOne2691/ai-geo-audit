## Problem
- **Одна учётка на всё.** migrate и api ходят в базу суперпользователем, которого заводит образ
  базы (Ч1.5а). Взлом api даёт право менять и удалять схему, исполнять команды в контейнере
  базы (`COPY … FROM PROGRAM`) и читать его файлы. ASVS 5.0 L2 требует служебных учёток с
  наименьшими правами — 13.2.2 по описи соседа.
- **Очередь без пароля.** Redis отвечает любому контейнеру сети `data`. С Части 3 в очередь
  пишет сервис, а читает воркер RQ; задачи RQ по умолчанию хранятся сериализованными pickle, и
  запись в очередь станет исполнением кода в воркере. ASVS L2 требует проверки подлинности при
  связи частей сервиса; слово владельца — к первому выкату база и очередь закрыты паролями.
- **Проверка старта не знает учётки процесса.** Адрес суперпользователя или роли миграций у
  api, адрес очереди без пароля — тихий старт. Правило длины пароля в бою есть только у базы
  (Ч1.2в, A21).
- **Пароли оседают там, где их не ждут:**
  - в журнале базы — текст упавшей команды вместе с паролем роли;
  - в строке процесса Redis и его проверки здоровья: на общем сервере её видит любой
    пользователь машины;
  - в `docker ps` и описании контейнера — если значение в команду подставил compose;
  - в выводе оракула и в журнале джобы `stack`: репозиторий открытый, журнал — тоже.

## In scope
- **Роли базы:**
  - `audit_migrate` — роль миграций, владелец базы `audit`. Через владельца базы ей
    принадлежит схема `public` (Postgres 15 и новее, по памяти — проба среза 0): она создаёт и
    меняет таблицы;
  - `audit_app` — роль сервиса у api и воркера: `SELECT`, `INSERT`, `UPDATE`, `DELETE` на
    таблицы и `USAGE`, `SELECT` на последовательности — уже созданные и, правами по умолчанию,
    будущие таблицы роли миграций в `public`. Права менять схему, `TRUNCATE`, `REFERENCES` и
    `TRIGGER` у неё нет;
  - у обеих — вход по паролю; не суперпользователь, без права заводить роли и базы, без
    репликации и обхода политик строк, без членства в других ролях.
- **Скрипт ролей** — `deploy/db/roles.sql`, файл psql без единого значения:
  - кто запускает. На пустом томе — сам образ postgres: каталог `/docker-entrypoint-initdb.d/`,
    суперпользователь образа, сокет, до открытия порта. На поднятом томе — та же команда psql
    через `docker compose exec db`: стенд, смена пароля, восстановление, каждый выкат (Ч1.6);
  - пароли — из окружения контейнера базы командой `\getenv`: `POSTGRES_MIGRATE_PASSWORD` и
    `POSTGRES_APP_PASSWORD`. Нет любого — отказ с именем переменной;
  - одна транзакция под замком миграций — ключ 1001 из реестра Ч1.2в; `lock_timeout` 120 с,
    как умолчание `MIGRATION_LOCK_WAIT_SECONDS`;
  - порядок: сначала роль миграций, затем роль сервиса — на нём держится проверка транзакции
    (A172, вторая строка);
  - сходится: роль заводится, если её нет; атрибуты и пароль ставятся каждый раз; у обеих
    ролей снимаются членства в других ролях. У роли сервиса сначала отзывается всё — на таблицы
    и последовательности `public`, на схему и базу, её права по умолчанию от роли миграций, — и
    выдаётся заново только нужное. Владелец схемы `public` — `pg_database_owner`; таблицы
    суперпользователя в `public` переходят роли миграций;
  - текст команд не попадает ни в журнал базы, ни в вывод psql: `\set ECHO none` первой
    строкой, `VERBOSITY terse`; сеанс выключает `log_statement`, `log_min_duration_statement` и
    `log_min_error_statement`.
- **compose:**
  - db: `POSTGRES_USER` и `POSTGRES_DB` — явно, как на main; две переменные паролей ролей —
    `${VAR:?причина}`; скрипт смонтирован только для чтения;
  - migrate и api: прежние переменные сервера `MIGRATE_DATABASE_URL` и `API_DATABASE_URL` —
    теперь адреса ролей `audit_migrate` и `audit_app`;
  - redis:
    - `REDIS_PASSWORD` — `${VAR:?причина}`;
    - `user: redis` — по имени пользователя образа, без чисел: у alpine и debian они разные.
      Стоит с Ч1.5б (L110). Правило `redis-auth` требует `user:` по имени, не root и не `0`:
      иначе «не от root» в боевом наложении держал бы только живой шаг, а наложение оракул не
      поднимает;
    - пароль — в настройках со входа, а не аргументом: `sh -c` с `exec redis-server - <<EOF` и
      строкой `requirepass $$REDIS_PASSWORD` внутри, без точки входа образа — при не-root она
      ничего не делает, звеньев меньше. Значение раскрывает оболочка контейнера;
      `redis-server` получает только `-`, в `Config.Cmd` — нераскрытое имя;
    - почему так — проба 12:39Z под правами Ч1.5б: точка входа без `user:` не стартует
      (`setpriv: setresuid failed`, код 127); root без неё — uid 0, `/data` не пишет и
      останавливается убийством (10 с, код 137); `user: redis` — uid 999, остановка за 0 с, код
      0, пароля нигде нет. Решение проверяющего 2026-11-19T12:44Z;
    - проверка здоровья берёт пароль из `REDISCLI_AUTH`, успех — только ответ `PONG`;
  - api: `REDIS_URL` — из переменной сервера `API_REDIS_URL`, адрес с паролем;
  - если боевое наложение уже в main — команда Redis в нём та же строка со входом, флаги
    `--maxmemory` идут после `-`; правило `redis-memory` Ч1.5в читает их из строки.
- **Проверка старта:**
  - таблица ролей процессов: `migrate` — `audit_migrate`, `api` и `worker` — `audit_app`. В бою
    имя в `DATABASE_URL` после раскодирования равно роли процесса, иначе отказ;
  - `REDIS_URL` в бою у `api` и `worker`: та же сверка двух разборщиков, что у адреса базы;
    пароль обязателен и не короче 12 знаков после раскодирования;
  - отказ — словами, без адреса и его кусков, в том числе без найденного имени: на месте
    имени бывает пароль.
- **Вычистка.** Новых секретов в процессах нет: пароли ролей и очереди приходят внутри

## Acceptance (observable)
- [ ] api ходит в базу ролью сервиса: данные читает и пишет, схему не меняет, `TRUNCATE` не
      может. migrate — ролью миграций, владельцем базы. Права сервиса на новые таблицы и
      последовательности роли миграций приходят сами.
- [ ] Роли появляются сами на пустом томе и той же командой на поднятом. Повтор отзывает лишнее
      у роли сервиса и больше ничего не меняет; повтор с новым паролем меняет пароль.
- [ ] Redis без пароля не отвечает, работает не от root, пароля нет в аргументах ни одного
      процесса; проверка здоровья входит с паролем и судит по ответу `PONG`.
- [ ] В бою процесс не стартует с чужой ролью базы или с адресом очереди без годного пароля;
      причина — словами, без адреса и пароля.
- [ ] Паролей нет в журналах, выводе, строках процессов и описаниях контейнеров — и тогда, когда
      скрипт ролей упал; в образце окружения — только заглушки.
- [ ] У каждого нового правила compose — код и проба. Имена ролей, переменных паролей, ключ и
      предел замка — одни в скрипте и в коде.

## Прогоны: семь вопросов

Шаг здесь — запуск скрипта ролей и подъём Redis с паролем. Шагов аудита нет.

| Вопрос | Ответ |
|---|---|
| 1. Повтор шага | скрипт ролей сходится: второй запуск отзывает лишнее у роли сервиса и больше ничего не меняет, кроме пароля, если он новый (A170). `up -d` без новых настроек ничего не пересоздаёт; migrate второй раз — код 0 (A66, Ч1.5а) |
| 2. Сбой и число попыток | скрипт сам не повторяется: первая ошибка — стоп, код 3, транзакция откатилась, пароля в выводе нет (A172). Упавший скрипт на пустом томе образ при следующем старте не повторит — каталог данных уже не пуст (документация образа postgres). База тогда стартует без ролей, migrate не входит: сбой громкий, с именем и кодом, как в A67. Лечится запуском той же командой через `exec`; повторяет человек или выкат |
| 3. Потолок | не относится: платных вызовов нет |
| 4. Обрыв посреди шага | скрипт — одна транзакция: обрыв оставляет прежнее состояние, повтор доводит до конца (A170, A172) |
| 5. Кто ещё меняет те же данные | скрипт и migrate берут один замок миграций, ключ 1001: разом не идут. На пустом томе migrate и не войдёт раньше конца скрипта: временный сервер начальной настройки слушает только сокет, а проверка здоровья db — по TCP (правило `db-health-tcp`, Ч1.5а). Два запуска скрипта разом — второй ждёт замка и идёт после первого; ждёт дольше `lock_timeout` 120 с — выходит с кодом 3 |
| 6. Двойное нажатие или запрос | не относится: кнопок нет; двойной запуск скрипта — вопрос 5 |
| 7. Тревога | не относится до Ч1.14: отказ громкий — код выхода и строка вывода; migrate без роли виден в `docker compose ps` (A67) |

## Безопасность

1. **Что появляется.**
   - Две роли базы с паролями; скрипт ролей в контейнере базы.
   - Пароль очереди: Redis не отвечает без него. Пароль — в настройках Redis со входа, в
     аргументах процессов его нет.
   - Новые переменные сервера: пароли двух ролей и очереди, адрес очереди у api; адреса базы
     migrate и api ведут на свои роли.
   - Проверка старта сверяет учётку процесса. Входов из сети нет. Данных заказчика нет.
2. **От кого защищаемся.**
   - Захват api — уязвимость в коде, будущее внедрение в запрос. С ролью сервиса только
     данные: схему не изменить и не удалить, `TRUNCATE` нет; команд ОС через
     `COPY … PROGRAM` и чтения файлов сервера базы нет — это права суперпользователя.
   - Сосед по сети `data`: будущий воркер, разовый контейнер, взломанный процесс. Без пароля
     он очередь не читает и не пишет, а запись в очередь RQ с Части 3 — исполнение кода в
     воркере.
   - Ошибка оператора: адрес суперпользователя или роли миграций у api; пароль очереди забыт
     или короткий; пароль подставлен в команду и ушёл в `docker ps` и журнал выката; ошибочная
     выдача прав, оставшаяся с прошлых запусков.
   - Утечка паролей: журнал базы при упавшей команде; строка процесса Redis и его проверки
     здоровья на общем сервере; вывод оракула и открытый журнал джобы `stack`; образец
     окружения в публичном git.
   - Не защищаемся: захват контейнера базы или Redis — там суперпользователь и пароль; root
     машины и права на докер; перехват внутри машины — шифрования нет, решение ведущей.
3. **Защиты этой поставки.** Каждая краснеет без своей защиты:
   - A85 — роль сервиса без права на схему и `TRUNCATE`; права на будущие таблицы и
     последовательности; роль миграций — не суперпользователь;

     пароль меняется повтором; база стенда переходит на роли без потери таблиц;
   - A171 — очередь без пароля не отвечает; redis — не от root, пароль не в аргументах;
     проверка здоровья — с паролем и по ответу;
