## Problem
- **Боевых отличий нет:** лимитов, журнала, переживающего пересоздание контейнера, потолка
  Redis, счёта соединений базы. Перезапуск упавшего процесса и мягкая остановка не проверены.
- **Предела мягкой остановки нет.** У api и db — умолчание докера 10 с, а мягкая остановка
  uvicorn — до 20 с (Ч1.3), базе нужно время на контрольную точку. По истечении срока докер
  убивает процесс.
- **Код 143 после остановки читать некому.** uvicorn 0.54 после мягкой остановки снова поднимает
  SIGTERM, и докер видит 143, а не 0. Без разбора остановка выглядит как падение — и у оракула, и
  у будущего сторожа Ч1.14.

## Users / stakeholders
- **Тот, кто выкатывает (Ч1.6).** Боевой файл накладывается на основной; Ч1.6 впервые поднимает
  их вместе на сервере.
- **6а-2.** Дополняет боевое наложение образами с сервера и своими правилами (A181) поверх этого
  файла.
- **Поставка «Учётки хранилищ».** Идёт сразу после этой: пароль очереди встаёт в ту же команду
  Redis, что и потолок `--maxmemory` наложения.
- **Сторож Ч1.14.** Берёт разбор остановки как есть: код 143 после остановки — не падение.
- **Часть 3.** Правило `db-connections` — сумма пулов против `max_connections` наложения.
- **Ведущая.** Принимает остановку, перезапуск и боевые правила.

## In scope
- **compose:** `stop_grace_period`: api — 30 с при мягкой остановке uvicorn 20 с (Ч1.3), db —
  60 с.
- **Разбор остановки** — `ai_geo_audit.ops.stop_verdict`: по коду выхода, записи uvicorn и
  команде остановки отличает «остановлен» от «упал». Код 143 после остановки — норма: uvicorn
  0.54 после мягкой остановки снова поднимает SIGTERM.
- **`docker-compose.prod.yml`** — боевые отличия поверх основного:
  - `mem_limit` и `cpus` у каждого сервиса — оценка, пересчёт после первого `docker stats`;
  - журнал — драйвер journald с меткой по сервису;
  - Redis — `--maxmemory` и вытеснение `noeviction`;
  - `max_connections` базы; сверка суммы пулов с ним — в Части 3, решение ведущей.
- **Правила compose** — `stop-grace` в основном наборе (A88) и три боевых (A89). Боевой набор
  включается флагом `--prod`. Семь правил основного набора из подписанных восьми дала 5б.
  - Порог `stop-grace` у api — предел uvicorn из `server_settings()` (20 с) плюс запас 10 с:
    30 с — норма, 29 с — красное, 15 с — красное (A88). Запас — именованная константа правила с
    причиной: закрытие пулов после мягкой остановки. Своего предела закрытия пулов в коде нет —
    `dispose_engine()` ждёт `engine.dispose()` без предела, — поэтому 10 с — оценка, строкой в
    decisions. Решение ведущей 2026-11-24.
  - Порог у db — 60 с, константа правила с причиной: контрольная точка Postgres. 60 с — норма,
    59 с — красное.
- **Оракул** — шаги остановки и падения api (A88) и правила на основном файле с боевым (A89);
  шаг A73 сверяет «сервисов 5, правил 24».

## Безопасность

1. **Что появляется.**
   - Боевое наложение: лимиты памяти и процессора у каждого сервиса, журнал в journald, потолок
     Redis, предел соединений базы.
   - Предел мягкой остановки api и db; разбор остановки в пакете.
   - Нового входа из сети нет.
2. **От кого защищаемся.**
   - Соседи на общем сервере: сервис без лимита забирает память и процессор машины.
   - Пропажа журнала при пересоздании контейнера: разбирать сбой не по чему.
   - Redis без потолка растёт до памяти машины; с вытеснением молча теряет задачи очереди.
     `noeviction` отказывает в записи явно.
   - Жёсткая остановка посреди записи: базе — 60 с на контрольную точку, api — предел uvicorn с
     запасом.
   - Упавший api без перезапуска лежит до человека.
   - Ошибка оператора: в боевом файле нет лимита, журнала или потолка — правила `--prod`.
3. **Защиты этой поставки.** Каждая краснеет без своей защиты:
   - A88 — перезапуск и мягкая остановка; разбор не путает остановку с падением;
   - A89 — лимиты и журнал у каждого сервиса, потолок Redis без вытеснения.
4. **Что проверит ведущая сессия своими пробами.**
   - Остановка api: `docker inspect` — код 143, запись uvicorn, перезапусков 0.
   - Падение uvicorn изнутри контейнера: перезапуск +1, снова healthy.
   - Правила с `--prod` на настоящих файлах и порчи наложения.
5. **Открытое.**
   - Первый живой подъём боевого наложения — Ч1.6: до неё опечатку в наложении ловят только
     правила по тексту.
   - Журнал journald окончательно — Ч1.6; выгрузка журнала с машины (Б27) — хвост Части 1.
   - Сторож здоровья судит остановку тем же разбором (A88): код 143 после остановки — не
     падение — Ч1.14.
   - Сумма пулов против `max_connections` (правило `db-connections`) — Часть 3, решение
     ведущей.
   - Замер лимитов под нагрузкой — этап 1.1, конец Части 5; повтор — Часть 13.
6. **Опора на опись защит соседа.**
   - З80 — лимиты, как у соседа; у него их держат тесты двух воркеров, у нас — правило у
     каждого сервиса; журнал — journald вместо `json-file` с ротацией (A89).

## Non-functional
- Боевое наложение оракул не поднимает: драйвера journald может не быть на машине. Его
  проверяют правила (A89); первый подъём — Ч1.6, на сервере.
- Числа лимитов — оценка, не замер; пересчёт — по замеру под нагрузкой (`docker stats`): этап
  1.1, конец Части 5; повтор — Часть 13.
- У каждого шага оракула свой предел времени.
- Строки до 100 знаков, кроме строк таблиц.
- **Чего защита не ловит.**
  - Опечатка в боевом наложении, которую правила по тексту не видят, всплывёт только при
    первом подъёме на сервере (Ч1.6).
  - Лимит — оценка: тесный лимит под нагрузкой убьёт процесс по памяти (код 137), его покажет
    замер этапа 1.1.
  - Перезапуск без предела числа: процесс, который падает на старте, крутится в `restarting`
    до сторожа Ч1.14.
