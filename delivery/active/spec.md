## Problem
- **Образа нет.** Сервис запускается только из рабочей копии. Выкат (Ч1.6) должен скачать
  готовый образ, собранный и проверенный в CI, а не собирать его на сервере.
- **Миграции.** В бою их гонят из того же образа одноразовым сервисом до API. Иначе API
  стартует на старой схеме, а сбой миграции проходит молча.
- **Секреты.** У соседа весь файл окружения уходит во все контейнеры. У нас каждый процесс
  получает ровно те секреты, которые требует его проверка старта, и не стартует без них.
- **«Образ собрался» — не «образ делает продукт».** У соседей в образ не попадали файлы пакета
  не `.py`, а консоль внутри образа не находила свой код. Нужен оракул на собранное.
- **Гейт контура** требует оракула на артефакт сборки (`artifact_oracle:`). У прошлых поставок
  там стоит «n/a: оракул придёт с образом Docker».

## Users / stakeholders
- **Тот, кто выкатывает (Ч1.6).** Одна команда поднимает базу, очередь, migrate и api; сбой
  назван по имени сервиса.
- **Ведущая.** Принимает поставку оракулом и своими пробами.
- **Исполнитель Ч1.5б.** Добавляет web, урезанные права, сети и боевые отличия в те же файлы
  compose, в те же правила и в тот же оракул.
- **Часть 3.** Воркер — тот же образ с другой командой.
- **«Оракул стека в CI».** Сразу после этой поставки, до Ч1.5б: уборка оракула при обрыве,
  два прогона разом, таблица шагов и джоба `stack` в структуре В1.

## In scope
- **Образ сервиса** — `deploy/backend/Dockerfile`, контекст — корень репозитория:
  - стадия установки: `uv` только на время сборки; сначала зависимости по `uv.lock`
    (`uv sync --locked --no-dev --no-install-project`), потом проект без редактируемой
    установки; окружение — в `/opt/venv`; Python берётся из базы, `uv` его не скачивает;
  - итоговая стадия: база `python` линии 3.12-slim; пакет, `alembic.ini`, `migrations/`;
    пользователь `app`, uid 10001, в `USER` — числом;
  - **версии образов:** тег линии и дайджест; берётся последний патч линии, который на день
    кода старше 14 суток; дату выхода смотрим при каждом добавлении и обновлении. Базы —
    с Docker Hub по дайджесту, решение ведущей: дайджест закрепляет содержимое, второй
    поставщик для сборки не нужен. Образ `uv` — из реестра его авторов, тоже по дайджесту;
  - **`uv` — исключение из правила патча, решение ведущей:** 0.11.26 везде — на машине, в CI
    и в образе: `uv.lock` пишет и читает одна версия. Обновление `uv` — осознанной правкой
    сразу в трёх местах.
- **Белый список контекста** — `deploy/backend/Dockerfile.dockerignore`: закрыто всё, открыты
  пять путей. После открытия снова закрыто на любой глубине: файлы окружения `.env*`, кэш
  Python, `.venv`, `node_modules`, `dist`.
- **`docker-compose.yml`:**
  - `name: ai-geo-audit`; сервисы db, redis, migrate, api; один образ на migrate и api;
  - порядок: db healthy → migrate завершился успешно → api; у migrate перезапуска нет, у
    остальных — `unless-stopped`; `init: true` у migrate и api;
  - проверки здоровья — числа: api — `interval` 10 с, `timeout` 5 с, `retries` 3,
    `start_period` 20 с; db — `pg_isready` по TCP, 5 с, 3 с, 12, 10 с; redis —
    `redis-cli ping`, 5 с, 3 с, 12, 5 с;
  - портов наружу нет ни у одного сервиса;
  - секреты — только окружением, `${VAR:?причина}`. У процесса — ровно переменные из его
    списка проверки старта; прочие настройки — только из полей конфига; у migrate и api —
    свои переменные сервера для адреса базы;
  - мастер-ключ — файлом-секретом, только у api;
  - `API_TRUSTED_PROXIES` у api — один адрес из переменной сервера `WEB_ADDRESS`: проверка
    старта api в бою требует её с Ч1.3; сам web с этим адресом — Ч1.5б.
- **Список процесса — открыто:** `startup_checks.required(process)` отдаёт имена, которые
  проверка старта требует от процесса. Правила читают его, а не закрытое поле модуля.
- **Проба здоровья** — `python -m ai_geo_audit.api.probe`: `GET /api/health` на своём порту
  с пределом 3 с, код 0 только на 200.
- **Правила compose** — `ai_geo_audit.ops.stack_rules` над выводом
  `docker compose config --no-interpolate --format json`. У каждого правила код; коды — в
  примерах A71 и A72.
- **Оракул** — `scripts/stack_oracle.py`, только стандартная библиотека: чистая копия
  `git archive HEAD` с канарейками, сборка, стек под своим именем, шаги примеров, уборка своего
  имени в конце прогона. Он первым путём стоит в строке `artifact_oracle:`. Ссылки гейта на
  номера его шагов даёт строка живого прогона в `eval-smoke.md`.
- **`.env.example`** — блок переменных стека с заглушками; **README** — стек и оракул.

## Out of scope
- **«Оракул стека в CI» — сразу после этой, до Ч1.5б:** A74 — уборка оракула при обрыве и
  остатки прошлого прогона; A75 — имена стека, два прогона разом, замок одной копии; A76 —
  таблица шагов, джоба `stack` в CI, ветка-проба. Решение ведущей: вынесено сразу, а не швом.
- **Ч1.5б:** образ фронта и nginx, заголовки и CSP, `/api/` через web; урезанные права
  контейнеров, сети без выхода наружу; боевые отличия — лимиты, журнал, Redis, соединения
  базы; остановка и перезапуск api.
- **Поставка «Учётки хранилищ» — сразу после Ч1.5б, в main до первого выката:** две роли
  базы и пароль очереди. Причина пароля — требование ASVS L2 о проверке подлинности при связи
  между частями сервиса и слово владельца: к первому выкату сервис защищён.
- **Ч1.6:** публикация образа по полному хешу, скачивание на сервере, файл окружения сервера,
  порядок отката со схемой, разбор конфига до `up -d`, проверка после выката, файл прокси
  хоста. Обычный порт на сервере открыт только для перенаправления и выдачи сертификата.
  Решение ведущей: туда же A68 и вторая строка A66.
- **Часть 3:** воркер и его здоровье. Правила для него — в плане, «Наследство для воркера».
- **Ч1.8:** Redis в проверке здоровья.
- **Часть 4:** браузер в образе. **Часть 10:** библиотеки и шрифты для PDF.

## Acceptance (observable)
- [ ] Образ собирается из чистой копии. В нём Python проекта, нет инструментов разработки,
      нет лишних файлов и секретов; файлы пакета — все; процессы — не от root; базы — по
      дайджесту.
- [ ] Новый стек поднимается одной командой: migrate до api, api healthy. Повтор migrate
      ничего не меняет. Сбой migrate назван по имени, api не стартует.
- [ ] Каждый процесс получает ровно свои секреты. У каждого правила compose — код и проба.
- [ ] Оракул проходит шаги всех своих примеров и в конце прогона убирает свой стек.

## Прогоны: семь вопросов

Шаг здесь — подъём стека и миграции. Шагов аудита нет.

| Вопрос | Ответ |
|---|---|
| 1. Повтор шага | `up` без новых образов и настроек ничего не пересоздаёт. migrate второй раз — код 0 и без изменений (A66). Оракул убирает свой стек в конце прогона; уборка остатков на старте — «Оракул стека в CI» (A74) |
| 2. Сбой и число попыток | migrate не повторяется: перезапуска у него нет, сбой громкий — имя и код, api не стартует (A67). У проверки здоровья числа названы: `retries`, `timeout`, `start_period` (A69). Сбой реестра при сборке — не код: упавшую джобу повторяет человек после конца прогона и с паузой. Перезапуск упавшего долгоживущего процесса — Ч1.5б |
| 3. Потолок | платных вызовов нет. Потолки памяти, процессора, журнала и соединений базы — Ч1.5б |
| 4. Обрыв посреди шага | migrate убит посреди ревизии — транзакция откатывается, база на прежней ревизии (Ч1.2б); следующий `up` гоняет migrate снова. Уборка прерванного оракула — «Оракул стека в CI» (A74) |
| 5. Кто ещё меняет те же данные | четыре migrate разом — замок Ч1.2в, его тесты на настоящей базе; проверка в стеке — Ч1.6 (A68). Две сессии — свои имена стека по пути копии; проверка двух прогонов разом — «Оракул стека в CI» (A75) |
| 6. Двойное нажатие или запрос | не относится: кнопок нет. Двойной `up` — вопрос 1, двойной migrate — вопрос 5, двойной оракул в одной копии — «Оракул стека в CI» (A75) |
| 7. Тревога | не относится до Ч1.14: здоровье видно в `docker compose ps`, его прочтёт сторож Ч1.14. Джоба CI — «Оракул стека в CI» (A76) |

## Безопасность

1. **Что появляется.**
   - Образ сервиса — то, что уедет в реестр и на сервер (Ч1.6).
   - Стек: база, очередь, migrate и api в сети compose. Входов из сети нет: портов наружу ноль.
   - Секреты процессов: адреса базы и очереди, секрет подписи — переменными окружения стека;
     мастер-ключ — файлом-секретом.
   - Данных заказчика нет.
2. **От кого защищаемся.**
   - Ошибка оператора: секрет не задан, лишний секрет у процесса, опечатка в имени настройки,
     порт наружу, сбой migrate проходит молча.
   - Утечка в образ: файл окружения, личные каталоги рабочей копии, тексты канона. Образ уходит
     в реестр.
   - Подмена базового образа или зависимостей между сборками.
   - Захват процесса внутри контейнера: процесс не от root. Урезанные права — Ч1.5б.
3. **Защиты этой поставки.** Каждая краснеет без своей защиты:

## Non-functional
- Оракул — только стандартная библиотека Python, вне пакета. На машине нужны Docker с
  compose v2 и BuildKit; правила оракул гоняет внутри собранного образа.
- Тесты бэкенда Docker не требуют: правила, разбор `Dockerfile`, таблица шагов и обвязка
  оракула проверяются без него; живой стек — оракулом. Пропущенных тестов 0.
- У каждого шага оракула свой предел времени: зависший шаг называется, а не висит.
- Оракул ничего не публикует наружу. Время в его выводе — UTC с Z.
- Шифрования внутри машины нет — решение ведущей: трафик между контейнерами идёт открытым
  внутри сети compose.
- Строки до 100 знаков, кроме строк таблиц.
- **Чего защита не ловит.** Белый список не спасает от секрета в открытом каталоге под
  незнакомым именем, например файла ключа в `backend/src/`: канарейки ловят только названные
  имена, такой файл держит сканер секретов волны В1. Правила видят файлы compose, а не правку
  руками на сервере: её ловит сверка после выката (Ч1.6). Дайджест держит повторяемость
  сборки, но не уязвимости базы образа — их ищет сканер из «Открытого». Сборка зависит от двух
  реестров — Docker Hub и реестра авторов `uv`: при отказе или лимите любого из них сборка
  падает, повтор — человеком.
