# Spec: подъём, сверка и откат стека (Ч1.6в и Ч1.6в3)

Вторая пара Ч1.6 — две поставки, 6в и 6в3; черновик для ведущей, 2026-11-19: 12:57Z, правка по
слову владельца 14:26Z — 14:30Z (`date -u`). Общее — `ch1-06-spec.md`; срезы по поставкам — план
пары. Ветка 6в — от main после 6а: ядро скрипта, `check` и файл окружения сервера уже есть; 6в3 —
сразу после первого выката. Буква «в» — новая: прокси хоста по-прежнему 6б.

| Поставка | Что делает | Примеры |
|---|---|---|
| **6в «Подъём, сверка и публикация»** | `up` с копией базы, `verify`, канарейка канала тревог, режим репетиции, живой прогон в `stack`; публикация образов и репетиция по реестру, памятка выката, разовые наблюдения готовыми командами | A180, A187, A188, A190, A191, A193–A196, A213, A23 |
| **6в3 «Откат и уборка»** | откат без схемы и со схемой, уборка своих образов, миграции в стеке, раздел отката в памятке | A197, A198, A211, A212, A23 |

Первому выкату нужна 6в: в ней и подъём, и публикация — без неё на сервере нечего скачать. 6в3
— сразу после первого выката, до второго с новым SHA: первому выкату откатываться не на что, стек
снимается `docker compose down` без томов.

## Problem
- **Стек на сервер нечем поднять.** Нет команды, которая по полному SHA и дайджестам ставит
  образы, снимает копию базы, сводит роли, гонит миграции и сверяет итог.
- **Один `up -d --wait` пересоздаёт api раньше, чем migrate кончит.** Сверено чтением исходника
  compose v5 (`pkg/compose/reconcile.go`, ветка main, 2026-11-19): пересоздание контейнера —
  фаза создания, ожидание `service_completed_successfully` — фаза запуска. Упал migrate — прежнего
  api уже нет.
- **Публикуется не тот образ, что проверен:** отдельная джоба собирает заново; путь «метка →
  дайджест → подъём» до сервера не исполняется нигде.
- **Отката нет:** ни на прежний образ, ни со схемой; свои старые образы копятся.
- **Канал тревог не проверен ни разу** — малая канарейка нужна при первом же выкате.

## Users / stakeholders
- **Ведущая** запускает `up`, `verify`, `rollback` по слову владельца; дерево переключает сама,
  видимой командой `git checkout`.
- **Владелец** видит каждый заход; даёт отдельное слово на смену пароля базы и на `downgrade`.
- **Ч1.14** — берёт метку «идёт выкат» и отправителя тревог; **Ч1.15** — каталог копий и рецепт.
- **6б** — ставит прокси перед поднятым стеком.

## In scope
- **`up <SHA> --backend-digest <D> --web-digest <D>`** — 6в. Дерево — уже на SHA: скрипт
  сверяет `HEAD == SHA` и чистоту дерева и сам его не переключает. Порядок — A187; migrate —
  отдельным разовым запуском до пересоздания api, внутри `up -d --wait` — второй, пустой проход.
  Путь образов — из адреса `origin` копии, владелец строчными; в файл сервера `up` пишет
  `<путь>@<дайджест>` — пометка «пишет выкат».
- **Копия базы** перед подъёмом — 6в, в корень копий из решения среза 0 6а, вне чужих каталогов.
- **Канарейка канала тревог** в конце удачного `up` — 6в, одно сообщение; сторож и тревоги о
  событиях — Ч1.14.
- **`verify`** — 6в: здоровье, образы, ревизия, бой и формат журнала, окружение, порты, журналы
  сервисов и `.deploy/` (`--logs`), системный журнал после пересоздания (`--journal`), сосед.
- **Режим репетиции** — 6в: только при `CI=true`, SHA — вершина копии, образы — прогона.
- **`rollback <SHA>`** — 6в3: на дайджесты прежнего выката из истории; со схемой —
  `--downgrade-to <ревизия>`, по отдельному слову владельца. **Уборка своих образов** — 6в3,
  держим три последних выката.
- **Публикация образов и репетиция по реестру** — 6в. Публикует та джоба, что собрала образы и
  прогнала на них оракул: сборка → шаги оракула → push ровно этих образов → скачать по дайджесту
  → репетиция скрипта на скачанных, с копией и восстановлением. Новых зависимостей нет: ни образа
  `registry`, ни действия артефактов.
- **Живой прогон скрипта против стека оракула** в джобе `stack` на запросе на слияние —
  «Исполнение рисковых путей» до слияния у обеих: в 6в — подъём, сверка, второй `up`, упавший
  migrate, пересоздание api, копия, снос и восстановление по рецепту памятки, команды разовых
  наблюдений (A213); в 6в3 — откат при одной записи истории и уборка.
- **Шаги оракула** — 6в3: A211 — `downgrade` и `upgrade` из образа; A212 — четыре migrate разом.
- **Памятка,** часть выката — 6в: `git checkout`, `up` под `tmux`, `verify`, смена пароля,
  рецепт восстановления копии; разовые наблюдения — готовыми командами с ожидаемым выводом,
  движком сервиса из контейнера api (A213). Раздел отката — 6в3.

## Out of scope
- **6а:** ядро, файл окружения, `check`. **6б:** прокси и сертификат.
- **Ч1.14:** сторож, тревоги о событиях. **Ч1.15:** копии по расписанию, внешняя копия,
  восстановление скриптом.
- **Часть 3:** воркер; ревизии, ломающие работающий код, и ревизии вне транзакции.

## Acceptance (observable)
- [ ] Выкат идёт только по полному SHA, дайджестам из итога публикации и дереву на этом SHA.
      Отказ любой проверки ничего не меняет.
- [ ] Упавший migrate не трогает прежний api; копия базы снята до подъёма.
- [ ] После выката: здоровье, образы, ревизия, бой, окружение, порты, журналы — сверены;
      канарейка дошла.
- [ ] Повтор выката ничего не пересоздаёт; смена пароля идёт по порядку; откат на прежний образ
      работает, со схемой — по слову.
- [ ] Публикуется ровно проверенный образ; путь «метка → дайджест → подъём» исполнен до сервера.
- [ ] Разовые наблюдения — готовыми командами памятки, их вывод сверен до сервера; `psql` руками
      не нужен.

| A23 | новые и изменённые файлы каждой поставки | сканер слов и поясов, связанных с РФ и РБ: 0 совпадений. **Чем:** тест |

## Прогоны: семь вопросов

Шаг здесь — выкат, сверка и откат стека. Шагов аудита нет.

| Вопрос | Ответ |
|---|---|
| 1. Повтор шага | `up` того же SHA ничего не пересоздаёт (A194); прерванный `up` доводит повтор той же команды (A180, третья строка) |
| 2. Сбой и число попыток | своих повторов нет. Реестр или Docker Hub не ответили — отказ до изменений (A187); повтор — человеком, после паузы. У `--wait` и каждой команды — предел времени. migrate не повторяется |
| 3. Потолок | платных вызовов нет. Ресурсы машины — `check` в начале `up` (A185); пять копий (A188); три последних образа (A197) |
| 4. Обрыв посреди шага | ход — сначала в `.deploy/`, дочерние процессы — в своей сессии: обрыв связи шаг не роняет. Долгий `up` идёт под `tmux new -d`, ведущая смотрит `last`. Копия — через временный файл; migrate и скрипт ролей — по одной транзакции; метка «идёт выкат» с номером процесса: мёртвый процесс — метка устаревшая, её снимает следующий запуск |
| 5. Кто ещё меняет те же данные | сосед — снимок до первого изменения и после (A186 6а). Два выката разом — замок (A187). Два migrate — замок Ч1.2в; в стеке — A212 |
| 6. Двойное нажатие или запрос | двойной `up` — замок; двойной `rollback` — замок и тот же итог |
| 7. Тревога | канарейка в конце `up` — одно сообщение (A190); отказ громкий — код выхода, шаг и причина в выводе и в `.deploy/`; метка «идёт выкат» — для сторожа Ч1.14 |

## Безопасность
1. **Что появляется.** Стек на общей машине на петле; копии базы на том же диске; образы в
   публичном реестре; одно исходящее сообщение в Telegram на выкат.
2. **От кого защищаемся.**
   - Ошибка оператора: не тот SHA, плавающая метка, сборка на сервере, правка `.env` без
     пересоздания, старый образ на новой схеме, выкат поверх идущего.
   - Подмена образа в реестре между публикацией и скачиванием — дайджест из итога джобы
     обязателен (A187).
   - Утечка токена бота: адрес с токеном не попадает ни в аргументы, ни в вывод (A190).
   - Вред соседу: перезапуск его контейнеров, его образы в нашей уборке.
   - Не защищаемся: от root машины; копии перед выкатом не шифруются до Ч1.15.
3. **Защиты этой поставки.** Каждая краснеет без своей защиты:
   - A180 — публикуется проверенный образ, путь «метка → дайджест → подъём» исполнен до сервера;
   - A187, A188, A190 — порядок, дайджесты, дерево на SHA, копия, migrate до пересоздания api;
   - A191, A193, A195, A196 — окружение, порты, журналы без секретов, журнал после пересоздания;
   - A194, A197, A198, A211, A212 — повтор, смена пароля, откат, уборка только своего, обратимость
     и замок миграций в образе;
   - A213 — разовые наблюдения движком сервиса, без `psql` и без значений в выводе.
4. **Что проверит ведущая своими пробами.** Вывод живого прогона в джобе `stack` и репетиции —
   строка за строкой с примерами; `docker pull` без входа и `docker history --no-trunc`; Id api до
   и после упавшего migrate в репетиции.
5. **Открытое.** Сторож и тревоги о событиях — Ч1.14; копии по расписанию и их шифрование —
   Ч1.15; ревизии, ломающие работающий код, — Часть 3.
6. **Опора на опись защит соседа.** З82 — образы собирает CI, сервер не собирает, как у соседа; у
   соседа сервер тянет метку `main`, у нас — только дайджест и только проверенный образ. Чего в
   описи нет, делаем сами: migrate до пересоздания api, сверка окружения контейнеров с файлом,
   копия перед migrate, уборка только своих образов, канарейка без токена в аргументах.

## Non-functional
- Скрипт — тот же `deploy/deploy.py` 6а; новые команды — `up`, `verify` (6в), `rollback` (6в3).
- Ожидание здоровья — `--wait` с пределом; у каждого шага — свой предел времени.
- Строки до 100 знаков, кроме строк таблиц и блоков команд.
- **Чего защита не ловит.**
  - Между публикацией и `up` реестр может ответить на метку иначе — тогда `up` отказывает, а не
    выкатывает: подмену ловит дайджест, но не предупреждает о ней раньше.
  - Отвечает ли прежний api во время повторного прохода migrate внутри `up`, не проверяется:
    проход пустой, ревизия та же.
  - Канарейка проверяет доставку одного сообщения, а не сторожа и не тревоги о событиях.
  - Копии перед выкатом — на том же диске и открытые до Ч1.15.
  - Подмена образа до публикации — внутри джобы CI — держат правила В1 о закреплённых действиях.
