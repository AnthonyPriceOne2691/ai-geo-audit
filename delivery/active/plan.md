**Гейт обязан что-то просудить**
- **Зелёный на пустоте** (грабли 1 и 8; реестр, стр. 95). Гейт без инструмента или по пустому
  входу выходит нулём. Поэтому у каждого гейта «просмотрено N > 0» (A91, A96, A98); шаг
  «инструменты на месте» ждёт `pip-audit`, `mutmut`, `vulture`, `lint-imports` (A103); пропуск
  теста — красный (A106).
- **Приёмка по прогону, а не по наличию скрипта** (грабли 7). `ci-oracles` пишется по
  зелёному прогону на коммите поставки, и это сверяет `check_ci_status.sh` (A114, A118).
- **Своя проверка без канарейки доктор пропускает** (грабли 11). Свои проверки этой поставки —
  тесты, а не скрипты в `scripts/lint/`. Если адаптация потребует канарейку — запись в
  `canaries.json` (A91).

**Одна область и одна версия**
- **Хуки и CI судили разные области** (реестр, стр. 94). `LINT_*` одни у хуков, CI и
  `adapted.json`; тест контракта сверяет, исключение одно и названо (A99).
- **Версии инструмента в дереве и в CI расходились** (реестр, стр. 87 и 96). Инструменты — только
  из dev-группы uv по lock, одна версия на машине и в CI; `pip install` в workflow — только uv
  точной версии (A99).
- **Локально зелено и зелено в CI — разные утверждения** (грабли 6). Доказательство поставки —
  прогон на GitHub; чистый клон остаётся проверкой проверяющего.
- **Общие `.venv` по ссылкам врут** (реестр, стр. 106; L6). Мутант импортируется из каталога
  мутантов, путь импорта печатается (A109). У рабочей копии своё окружение.

**Payload и снимки**
- **Извлечение пишет поверх файлов** (грабли 4). Payload извлекается во временную папку ОС, в
  репозиторий копируются файлы payload.
- **Линтеры проекта переписывали скрипты контура** (грабли 10). ruff, mypy и форматтер не
  смотрят в `scripts/lint/` и другие файлы payload; иначе тело разойдётся с замком (A92, A93).
- **Ратчет снимков требует точного совпадения** (реестр, стр. 97). Снимки пересобираются после
  последней правки поставки; рост — только подписью человека (A102).
- **Снимок нельзя пересоздать вверх ради зелёного** (грабли 2). Мягкий режим и снятый гейт в
  CI запрещены тестом контракта (A99, A103).

**Слияние и ветки**
- **Необязательная проверка — совет, а не гейт** (реестр, стр. 110). Обязательные — по именам
  `gates`, `delivery`, `tests`; защита действует и на владельца (A116).
- **Ждать CI по последнему прогону на этом коммите** (реестр, стр. 101). `check_ci_status.sh`
  последним в `merge_guard.sh` (A114). Ожидание по составу проверок — В1в.
- **Отмена прогона на хеше выката** (реестр, стр. 108). На main прогон не отменяется и не
  вытесняется следующим: группа по хешу коммита (A101).
- **Ветку запроса не перебазировать, конфликт выключает CI** (реестр, стр. 98 и 99). main
  вливается в ветку; первым делом смотрим, сливается ли запрос (Rollout).
- **Слияние руками, уборка по порядку** (реестр, стр. 100). Слияние — по полному хешу вершины;
  рабочая копия снимается до слияния, ветка — после того, как запрос слит (Rollout).
- **Строки параллельных запросов в одном месте ломают слияние** (реестр, стр. 107). Строки
  STATUS этой поставки — только в её STATUS; объявления переносятся дословно.
- **Каждый коммит разреза зелёный сам по себе** (реестр, стр. 115). Срез — свои коммиты, тест

## Approach

Шесть срезов. Каждый — свои коммиты; тест сначала красный, потом зелёный. Срез 0 кода не
пишет: его итог — записи в decisions до первой строки кода.

**0. Замер до кода.**
1. Payload канона — во временную папку ОС. Число файлов `scripts/**` сверяется с правилом
   канона «не меньше 43».
2. Гейты канона — по копии main без правок. По каждому гейту — число нарушений и правки в
   строках файлов. Больше 80 строк правок — сразу поставка «правки под гейты» до В1а:
   отсечка обязательна. Те же гейты — по вершине ветки Ч1.3 `ch1-03-api-entry`, только
   чтением, в отдельном клоне: находки по её коду — одним сообщением проверяющему, правят «руки»
   у себя до сдачи.
3. mutmut на раскладке `backend/src`: корень импортов, `also_copy` с `tests/`. Не встаёт —
   адаптация с замером или объявление с причиной; тогда долг свойства A111 остаётся неполным,
   и это пишется в STATUS.
4. Покрытие подпроцесса на одной ревизии: `patch = ["subprocess"]`, слияние файлов
   подпроцессов, нужны ли гринлеты в `concurrency`. Там же: тест A22 Ч1.2б сверяет точное
   множество ключей окружения подпроцесса — под покрытием в нём могут появиться свои
   `COVERAGE_*`.
5. `filterwarnings = ["error"]` в настройках pytest: предупреждения coverage, hypothesis и
   mutmut станут ошибками — прогон с ними до кода.
6. `pip-audit` по `requests==2.31.0`: сколько записей насчитает гейт — три или шесть (A102).
7. `uv lock` с `exclude-newer` и тремя исключениями: какие пакеты сдвинутся (A121).
8. ruff, mypy и форматтер не смотрят в файлы payload.
9. detect-secrets 1.5.0 на Python 3.12: на PyPI у него не указан `requires_python` — хук и
   снятие `.secrets.baseline` проверяются на нашем окружении до кода. Там же: ловит ли он
   пароль в адресе с пустым именем (`redis://:…@…`) — у соседа не ловит (A122).
10. Поведение GitHub, которое спека взяла по памяти: `mergeStateStatus` у запроса (A98), поля
    защиты ветки в API (A116). Сверка — по документации GitHub, до кода, а не на приёмке.
    Запрос страницы — через окно прав владельца.

**1. Ось ② (A90–A97, A120, A121).**

  `--lock-only` из папки канона: при разошедшихся записях он отказывает.

  `config-access` с `LINT_PY_SRC=backend` (A94), `detect-secrets` (A96) и AST-гейт с правилом
  `inline-prompt` — его граница названа в A120.
- Внешних хуков нет, все — `repo: local` из dev-группы (A100). detect-secrets — локальным хуком.
  Пять проверок гигиены — `check-yaml`, `check-json`, `check-toml`, `check-merge-conflict`,
  `check-added-large-files` — пакетом `pre-commit-hooks`, с теми же id, `language: system` через
  `uv run`. Смена транспорта — запись в `adapted.json`.
- `.secrets.baseline` — командой канона после `git add`. Если сканер метит публичный пароль
  стенда — запись с причиной.
- Фрагмент канона влит в `backend/pyproject.toml`; там же:
  - свой `[tool.coverage.run]`: `source` — `src` и `migrations`, `patch` — `subprocess`;

    `required-version = "==0.11.26"`: чужая версия uv отказывает, lock не трогает (A123);

- `backend/.importlinter` — слои сверху вниз: вход API, `storage`, `logs`, `config`.
- Объявления: TS-половины — с причиной «поставка В1б»; адаптации — с причиной.
- Снимки — один раз `--generate`, ноль там, где код чистый.
- Правки под гейты — не больше 80 строк; сверх — отсечка до В1а.
- `pre-commit install --allow-missing-config` с pre-push.
- `README.md` — как гонять гейты; команды настроек GitHub для проверяющего, без адресов.
  `AGENTS.md` — указатель на CQG.

## Stack / boundaries

**Правило версий** (проверяющий, для всех полос): пакет моложе 14 суток не берём; дату выхода
смотрим при каждом добавлении и обновлении; исключение — словом проверяющего, с причиной в
decisions. Версии ниже сверены по первоисточникам 2026-11-19, все старше 14 суток.

**Новые инструменты — dev-группа uv. Нужно слово владельца, одно на список.** Каждый — строкой
`new_dependency: … by=human:owner` в STATUS.
- ruff 0.17.3 — линтер, форма кода, гейты сложности;
- mypy 2.4.1 и types-PyYAML 6.0.12.20261103 — проверка типов;
- pre-commit 4.7.0 — запуск хуков;
- detect-secrets 1.5.0 — секреты в коммитах;
- pip-audit 2.10.1 — известные уязвимости зависимостей;
- mutmut 3.8.1 — мутационный гейт;
- pytest-cov 7.1.0 и coverage 7.17.2 — покрытие изменённого и подпроцессов;
- hypothesis 6.170.14 — свойства с генератором входов;
- import-linter 2.15 — гейт слоёв;
- vulture 2.16 — мёртвый код;
- PyYAML 6.0.3 — разбор workflow в тесте контракта;
- pre-commit-hooks 6.0.0, выпуск 2025-08-09, Python от 3.9 — пять проверок гигиены локальными
  хуками. Тянет ruamel.yaml: её версия — по lock под `exclude-newer`.

pytest-env из списка канона не берём: окружение тестов держит Ч1.2в (A31). Это объявленная
адаптация.

**Свежие пакеты, которые уже стоят** — исключением `exclude-newer-package` с причиной: в lock
они были до правила. sqlalchemy 2.1.9, pydantic-settings 2.16.3, pytest-asyncio 1.5.0.

**Установка пакетов.** При `uv add` ставится `--exclude-newer` с датой «сегодня минус 14
суток»: свежее не подберётся само. В В1а это становится постоянной настройкой `[tool.uv]` в
`backend/pyproject.toml` (A121); дата двигается рукой при каждом обновлении lock.

**Инструменты CI — не пакеты проекта. Нужно слово владельца:**
- `actions/checkout` v7.0.1 — коммит `3d3c42e5aac5ba805825da76410c181273ba90b1`;
- `actions/setup-python` v7.1.0 — коммит `6d4fd22b20465ccc0f7354476588e8df7c9ca0e0`;
- хеш сверен со страницей релиза и API; в workflow — полный хеш, метка версии в комментарии;
  других действий нет;
- внешних хуков pre-commit нет: все `repo: local` (A100);
- uv 0.11.26 везде: на машине, в CI и в образе (Ч1.5а). В CI ставится `pip install
  uv==0.11.26`, без стороннего действия; `required-version` в `[tool.uv]` держит ту же версию
  (A123);
- образ службы `postgres:16-alpine` — с зеркала, как у соседа, по дайджесту. Зеркало и дайджест
  выбирает проверяющий. 14 суток — по дате выхода версии программы (16.x), а не по перезаливке
  метки: перезаливки несут исправления системных пакетов. Дайджест — текущий на день кода,
  одинаковый на Docker Hub и на зеркале; сверка и дата — в decisions. Меняется только осознанной
  правкой; страхует сканер образа;
- раннер `ubuntu-24.04`, а не `ubuntu-latest`: образ раннера не меняется под нами молча.

**Сканер образа — не В1а.** Trivy, отдельной малой поставкой волны В1 сразу после Ч1.5а:
файл выпуска — по контрольной сумме, подпись сверена по существу до первого запуска; задание
сканера без секретов, токен только на чтение; их действие GitHub не используем.

**Настройки GitHub — выполняет проверяющий по слову владельца, одной командой на настройку.**
«Руки» их не трогают; команды — в README:
- защита main: обязательные `gates`, `delivery`, `tests`; `strict`; защита и для владельца;
  запрет force-push и удаления; обязательных одобрений нет;
- права токена по умолчанию — только чтение; Actions не создают и не одобряют запросы;
- запуск workflow из чужих копий репозитория — только после одобрения;
- разрешённые действия — GitHub и поимённо названные.

**Публичный репозиторий и секреты:**
- **что CI видит из секретов** — ничего: секретов репозитория нет, `secrets.` в workflow нет
  (A100). Пароль службы Postgres — публичный пароль стенда, база живёт только в прогоне;
- **что видит чужой запрос** — событие `pull_request`: токен только на чтение, секретов нет, до
  одобрения владельца прогон не стартует. `pull_request_target` запрещён тестом (A100).
  `main-guard` срабатывает только на push в main и кода ветки не исполняет;
- **права токена прогона** — `contents: read` сверху каждого workflow; `issues: write` — только
  у джобы `alert`, без checkout; `persist-credentials: false` — токен не остаётся в
  `.git/config` для следующих шагов;
- **что уходит наружу толчком** — ветка поставки и ветки-пробы, толкает проверяющий после
  скана правки и сообщений коммитов, на каждом толчке.

**Границы:**
- payload — дословно. Тела скриптов В1а не правит; адаптации — только объявленные, в
  `adapted.json`;
- свои проверки — тестами, а не новыми скриптами в `scripts/lint/`: бюджет 23 гейтов из 23
  исчерпан;
- `frontend/` поставка не трогает; TS-половины и JS-половина аудита — объявления до В1б;
- `delivery/`, `.github/workflows/`, `.pre-commit-config.yaml` и `scripts/lint/` гейт поставки не
  считает: их читают глазами и сверяют с каноном и замком.

## Rejected alternatives
- **Одна поставка В1 целиком** — отвергнута, потому что вместе с фронтом выходит около 1000
  строк по гейту и до 26 файлов. Первые круги CI будут красными, и npm в них лишний.
- **Тесты отдельным workflow** — отвергнуто, потому что `main-guard` слушает только `quality`:
  красные тесты main не открыли бы задачу. Второй файл — ещё одно место для прав и хешей.
- **Покрытие и мутации в джобе `gates`, как в шаблоне** — отвергнуто, потому что каждому прогону
  pytest нужна база: без Postgres сессия тестов останавливается на старте, мутантов судить
  нечем.
- **Каталог миграций вне покрытия (`omit`)** — отвергнуто, потому что ослепит гейт и к `env.py` с
  замком миграций. Это запасной путь, только если пробы среза 0 не зеленеют: с причиной и
  долгом в STATUS.
- **Ревизии в процессе теста** — отвергнуто, потому что спорит с решением Ч1.2б «той же
  командой, что в бою» (A22) и с уроком L19.
- **Действия по метке, как в шаблоне** — отвергнуто, потому что метку перевешивают на другой
  коммит, и чужой код получает токен (Б22).
- **Внешние хуки pre-commit, даже по хешу** — отвергнуто, потому что хук ставит своё окружение и
  тянет зависимости с PyPI свежими — мимо lock, хешей и правила 14 суток, без слова владельца.
- **Пять проверок гигиены своим тестом, без пакета** — отвергнуто, потому что это меняет состав
  конфига хуков, а канон даёт менять только транспорт, пути и версии; к тому же проверка ушла бы
  с коммита в pytest. Свой скрипт в `scripts/lint/` — тоже нет: это механика канона.
- **`main-guard.yml` дословно** — отвергнуто, потому что право записи сверху расходится с
  правилом A100, а `ubuntu-latest` меняется под нами. Адаптация — с записью.
- **JS-половина аудита сразу в В1а** — отвергнуто, потому что critical и high у npm покрасили бы
  В1а кодом фронта, а при недоступном реестре JS-ветка молча даёт нули. Своё правило для неё —
  в В1б.
- **Стороннее действие установки uv** — отвергнуто, потому что действие исполняется рядом с
  токеном. uv ставится пакетом точной версии.
- **Разбор workflow регулярными выражениями** — отвергнуто, потому что якорь YAML или запись в
  одну строку прячет `uses:` от регулярки. Регулярка — только для комментария версии, в одном
  месте.
- **Проба сканера закрытым ключом PEM** — отвергнута, потому что ветка-проба публична навсегда,
  а защита отправки GitHub может её не пропустить. Хватает ключевого слова и случайных знаков.
- **Пропуск теста ловить флагом CI** — отвергнуто, потому что правило тогда действует только в
  CI. Хук в `conftest.py` одинаков на машине и в CI.
- **Обязательное одобрение в защите ветки, как в готовой команде канона** — отвергнуто, потому
  что учётка одна, а одобрить свой запрос GitHub не даёт: ни один запрос не слить. «Проверяющий
  не исполнитель» держат поле `verifier:` и гейт поставки.
- **Серьёзность Python-уязвимостей из внешней базы оценок** — отвергнуто, потому что при нулевом
  снимке она не нужна: краснеет любая запись.
- **pytest-env по списку канона** — отвергнуто, потому что окружение тестов уже держит Ч1.2в
  (A31). Два механизма — два источника правды.
- **Последние версии с PyPI** — отвергнуто, потому что только что выпущенная версия — риск
  цепочки поставки (правило 14 суток).
- **Ветку толкает исполнитель** — отвергнуто, потому что первый толчок публичен навсегда: до него
  нужен скан правки у проверяющего.
- **Проба толчком прямо в main** — отвергнута (решение проверяющего): если защита не встала,
  пустой коммит остаётся в публичной истории. Хватает чтения настроек (A116).
- **Настройки GitHub меняют «руки»** — отвергнуто, потому что это граница доступа: её двигает
  проверяющий по слову владельца.

## Risks
- **Калибровка объёма.** Множитель 1,3 — одна точка, у Ч1.2б вышло 1,74, у Ч1.3 — 2,03. Поэтому
  разрез — до среза 1 (решение проверяющего 2026-11-19T13:21Z); пересчёт по замеру среза 0 — в
  «Оценке объёма».
- **Адаптации тел payload.** `check_deps_audit.sh` и глоб гейта мутаций правятся с записью в
  `adapted.json`: доктор показывает WEAK с причиной, при обновлении канона правку переносить.
  Обе — находки канона.
- **Бюджет мутаций на раннере.** Один воркер: на машине 220 с на 272 мутанта двух модулей при
  бюджете 300. На раннере запас не подтверждён — время покажет первый прогон CI.
- **mutmut на раскладке `backend/src`.** Канон мерил плоскую раскладку; `also_copy` по умолчанию
  берёт `tests/` от корня импортов, а такого каталога нет. Проба — срез 0. Не встаёт —
  адаптация с замером или объявление с причиной, и долг свойства остаётся неполным (A109).
- **Покрытие подпроцесса.** Слияние файлов подпроцессов и гринлеты ревизий проверены только
  чтением кода coverage. Тест A22 сверяет точное окружение подпроцесса и может покраснеть под
  покрытием. Проба — срез 0; запасной путь — `omit` с причиной (A107, A108).
- **Предупреждения как ошибки.** `filterwarnings = ["error"]`: новый инструмент с предупреждением
  роняет тесты. Проба — срез 0.
- **detect-secrets на Python 3.12.** Версия 1.5.0 не называет поддерживаемый Python. Проверка —
  срез 0. Не работает — это вопрос к проверяющему: замена сканера потребует слова владельца.
- **Правки под гейты.** Код Ч1.1–Ч1.3 писался «как у ruff», но гейты сложности и типов его не
  видели. Больше 80 строк — поставка до В1а.
- **Первые прогоны CI красные несколько кругов** (план раскатки). Чинится причина, а не гейт:
  отключить, смягчить или переснять снимок вверх нельзя.
- **Объявления TS-половин при живом фронте.** Если доктор сочтёт их ложью — В1б идёт следом
  без перерыва, а проверяющий видит причину на каждом прогоне (A91).
- **Шаг «Инструменты гейтов на месте» ждёт eslint и jscpd**, раз во фронте есть `package.json`,
  а npm в CI В1а нет. Форма объявления TS-половин должна быть той, которую шаг читает; иначе
  он краснеет на верной настройке. Сверка — по тексту шага в срезе 1.
- **`exclude-newer` сдвинет lock.** `uv lock` с датой может опустить версии транзитивных
  пакетов: дифф lock смотрим в срезе 0, тест A121 сверяет итог.
- **`.secrets.baseline` и ложные находки.** Сканер может пометить публичный пароль стенда —
  запись с причиной, а не выключение сканера.
- **Число записей у `requests` 2.31.0** гейт считает по-своему: три уязвимости или шесть
  идентификаторов. Строка A102 требует N ≥ 3; точное число — в срезе 0.
- **Строки STATUS на main после сдачи.** Активной поставки нет: шаг подписи это разбирает
  (A105). Проверку новых зависимостей на первом слиянии под CI смотрим на слитом состоянии
  (`DRY_RUN=1 merge_guard.sh`) до сдачи.
- **Сканер A23 по payload канона.** Совпадения называются поимённо, тела не правятся.
- **Хеши действий.** Ошибка в хеше даёт отказ прогона «не найдено действие» — громко и дёшево.
  Хеш берёт и сверяет один человек.
- **Поведение GitHub по памяти** — `mergeStateStatus`, поля защиты ветки. Сверка по документации
  — срез 0; расхождение правит строки A98 и A116 до кода.
- **Чужое предупреждение об уязвимости роняет все открытые запросы** обеих сессий. Починка —
  отдельным запросом, одним пакетом в lock (A103).
- **Общая машина.** Мутационный гейт тяжёлый: локально — при нагрузке ниже 12, один прогон на
  рабочую копию.

## Rollout / migration
1. Ветка от main, когда в main лежат Ч1.2в, Ч1.2г, Ч1.4а и Ч1.4б; Ч1.3 идёт параллельной полосой
   (порядок полос по слову владельца 2026-11-19T12:29Z). Поставка «правки под гейты», если она
   нужна, слита раньше. Рабочая копия поставки — своя. Кто из В1а и Ч1.3 сдаётся вторым, тот
   вливает main слиянием и гоняет гейты на слитом; правки кода Ч1.3 под гейты сверх 80 строк —
   отсечка, сразу проверяющему.
2. **Порядок сдачи:** исполнитель сдаёт проверяющему локально → проверяющий сканирует правку и
   сообщения коммитов и бегло читает → толкает ветку и открывает запрос на слияние → прогон →
   приёмка проверяющего с пробами → вердикт и подписи → слияние словом и пальцем владельца.
3. **Каждый новый толчок ветки** — снова после скана, а не только первый. Ветки-пробы — тоже
   публичны: только порчи из плана, без данных и имён; толкает их проверяющий.
4. Перед любым `gh` и push — статус пальца отдельной командой, потом сама команда.
5. Порядок записей: `cqg@3.14` в конституции и приёмке стека → замок `--lock-only` → доктор.
6. `pre-commit install --allow-missing-config` с pre-push — в каждой живой рабочей копии,
   включая ветки, отведённые до В1а.
7. Первый прогон: `ci-oracles` и строка конституции — по факту этого прогона, в том же коммите
   (Delivery §10.4).
8. Настройки GitHub — проверяющий по слову владельца, одной командой на настройку, команды — в
   README. Защита main — после первого зелёного прогона ветки: до него GitHub не знает имён
   проверок. Потом — чтение настроек (A116). Толчка прямо в main для пробы нет.
9. Слияние: `DRY_RUN=1 merge_guard.sh`, затем `gh pr merge --squash --match-head-commit <полный
   хеш>`, как в каноне. В сообщении слитого коммита — полный хеш вершины, которую принял
   проверяющий. Вердикт и подписи живут в архиве поставки. После — сверка main по файлу и хеш
   командой. Рабочая копия снимается до слияния, ветка — после того, как запрос слит.
10. Открытые ветки других поставок вливают main в себя и проходят хуки; их следующий запрос
    идёт через гейты.
11. Поставка отсечки — свойства A112 и A119 — открывается сразу после слияния В1а.
12. Ветки-пробы закрываются без слияния и удаляются; временные копии и их базы — тоже. Строка
    «убрано» — в сдаче.
13. Откат: обратный коммит слияния В1а отдельным запросом. Тем же запросом возвращаются
    `ci-oracles` в STATUS и строка CI в конституции: иначе они солгут. Настройки GitHub
    возвращает проверяющий по слову владельца.
