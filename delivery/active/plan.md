## Approach

Срез 0 без строк кода и пять срезов кода. Каждый срез кода — отдельные коммиты; тест или шаг
оракула сначала красный, потом зелёный. Шаги каждого среза — в таблицу шагов, их номера — в её
тест в том же срезе (команда ведущей 2026-11-23T10:47Z). Мера — до коммита кода (L103).

**0. Числа наложения и порог `stop-grace` — до кода, строками в decisions.**
- `mem_limit` и `cpus` пяти сервисов, `--maxmemory` Redis, `max_connections` базы — оценка по
  `docker stats` стека оракула на машине (простой и прогон шагов) и по лимитам соседа (З80);
  пересчёт — этап 1.1.
- Метка журнала по сервису — вид значения `tag` драйвера journald, по документации докера.
- Порог `stop-grace` у api — открытый вопрос спеки; решение проверяющего — до среза 1.

**1. Предел мягкой остановки и правило `stop-grace` (A88, третья строка; A87 — счёт 24).**
- compose: `stop_grace_period` — у api 30 с, у db 60 с.

## Stack / boundaries
- **Новых пакетов нет:** hypothesis уже в окружении тестов (В1а); образы — прежние.
- **Граница:**
  - правила читают предел мягкой остановки из кода (`server_settings()`), а не из копии числа;
  - разбор остановки — в пакете: его возьмёт сторож Ч1.14;
  - боевой файл — только наложение: основной файл без него поднимается как прежде.
- **Гейт контура:** рисковый путь в STATUS один — `docker-compose.prod.yml`; строка
  `artifact_oracle:` — `scripts/stack_oracle.py`; тест таблицы шагов называет номера шагов этой
  поставки.
- **Гейты В1а и контур `delivery@2.30`:** код в `backend/src` — mypy strict, сложность с пустым
  снимком, AST-гейты; в CI — покрытие изменённых строк не ниже 70 % и порчи всего изменённого
  файла не ниже 60 % за 1200 с: `stack_rules.py` (419 строк) мутируется целиком, правка
  `ops/__init__.py` берёт весь пакет `ops` (L98). Оракул в `scripts/` — ruff и mypy strict с
  конфигом backend; CI его покрытие не мерит — замер руками. Длина файла — до 500 строк. STATUS —
  `ci-oracles: deployed`; вердикт — только «- [x] READY FOR HANDOFF».

## Rejected alternatives
- **`json-file` с ротацией, как у соседа,** — отвергнут для боя, потому что журнал пропадает
  при пересоздании контейнера. Предварительно — journald (решение ведущей).
- **Ждать код 0 при остановке api** — отвергнуто, потому что uvicorn 0.54 после мягкой
  остановки снова поднимает SIGTERM: нормальная остановка — 143 с записью uvicorn (A88).
- **Проверить перезапуск командой `docker kill`** — отвергнуто: это ручная остановка, политика
  `unless-stopped` её не перезапускает (L71 второго соседа). Падение — изнутри контейнера.
- **Поднимать боевое наложение в оракуле** — отвергнуто, потому что драйвера journald может не
  быть на машине: наложение проверяют правила, первый подъём — Ч1.6.
- **Правило `db-connections` здесь** — отвергнуто решением ведущей: сумма пулов впервые растёт с
  пулом воркера — Часть 3.
- **Боевые правила в `stack_rules.py`** — отвергнуты: файл 419 строк при пределе 500, а
  правила наложения — свой набор под флагом; отдельный модуль, как `stack_hardening.py` у 5б.

## Risks
- **journald на машине может не быть** — боевое наложение проверяют только правила.
- **Числа в выводе compose.** `mem_limit` приходит в байтах, `cpus` — числом; правило
  `limits` сравнивает числа, а не строки файла.
- **Команда Redis в наложении.** `command` при наложении заменяет команду основного файла
  целиком. «Учётки хранилищ» ставят пароль очереди так, что `--maxmemory` наложения встаёт рядом
  (их разбор); `redis-memory` и будущий `redis-auth` судят слитый вывод с `--prod`.
- **Порядок шагов оракула.** Шаги A88 ломают api: стоят после шагов web и защиты стека и
  возвращают api healthy, иначе следующие шаги краснеют не по своей причине.
- **Соседние поставки.** «Учётки хранилищ» и 6а-2 дополняют те же compose, правила и наложение:
  их счёт правил идёт от 24 и 27. При открытии их веток — сверка чисел.
- **Если uvicorn вернётся к коду 0,** разбор остановки его уже принимает.

## Rollout / migration

- Сразу после этой поставки — «Учётки хранилищ», затем Ч1.6; 6а-2 дополняет наложение образами
