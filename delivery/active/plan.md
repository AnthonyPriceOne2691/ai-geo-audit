**Роли базы**
- **Одна учётка на всё — у соседа хуже, чем в описи** (опись, З75; сверка описи, п. 31): адрес
  один на все сервисы бэкенда, имя в нём — суперпользователь образа базы, а он исполняет
  команды ОС в контейнере базы. У нас у api — роль сервиса, у migrate — роль миграций,
  суперпользователя нет ни у одного процесса (A85, A174).
- **Тест прав — на настоящей базе** (указатель уроков: всё, что уходит в базу, проверяется на
  настоящей базе; опись, Б18 — «тест прав»). Права проверяет оракул в стеке — на образе и томе,
  как в бою, а не разбор текста скрипта (A85).
- **Права на последовательности, `TRUNCATE` и `REFERENCES`** (чтение спек Ч1.5, п. 2.10): без
  прав на последовательности первая же вставка в таблицу с ключом `bigserial` падает. Проба
  вставляет строку без ключа; `TRUNCATE` — отказ; `REFERENCES` и `TRIGGER` у роли сервиса нет
  (A85, третья строка).
- **Миграцию гоняют тем, чем её гонят в бою** (журналы соседа, Р22): права сервиса проверяются
  на таблице, которую в живом стеке создала роль миграций своим адресом (A85, третья строка).
- **`CREATE` на `public` у `PUBLIC` отозван с Postgres 15** (чтение спек Ч1.5, п. 11.7 — по
  памяти): владелец базы получает схему через `pg_database_owner`. Это проба 1 среза 0; скрипт
  всё равно отзывает `CREATE` явно и ставит владельца схемы — на случай восстановленной базы.
- **Скрипты начальной настройки образа идут только на пустом каталоге данных** (документация

  тот же файл через `exec` на поднятом томе — и ответ на вопрос 2 о прогонах.
- **Нововведение проверяется на стенде от состояния боя** (указатель уроков, «Стенд до выката

## Кто и какой командой создаёт роли

**Скрипт начальной настройки базы — `deploy/db/roles.sql`; исполняет его psql
суперпользователем образа postgres.** Один файл, два пути:
- **пустой том** — сам образ. По его документации (прочитана 2026-11-19) файлы `*.sql` из
  `/docker-entrypoint-initdb.d/` исполняет psql под `POSTGRES_USER`, а временный сервер
  начальной настройки слушает только сокет: порт открывается после. Новый сервер, оракул и
  джоба `stack` получают роли без отдельного шага;
- **поднятый том** — та же программа руками или выкатом:

  ```
  docker compose exec -T db sh -c \
    'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
      -f /docker-entrypoint-initdb.d/roles.sql'
  ```

  Её зовут: стенд при переходе на эту поставку, смена пароля, восстановление копии (Ч1.15) и
  каждый выкат — до подъёма migrate и api (Ч1.6). Каждый запуск сводит роли к одному виду:
  лишнее у роли сервиса отзывается, нужное выдаётся заново.

**Где пароли.** В файле окружения сервера. compose отдаёт их только контейнеру db —
`${VAR:?причина}`; psql читает их командой `\getenv` из окружения своего процесса. В git —
только имена переменных и заглушки `CHANGE_ME` в образце. Образ db — образ postgres без правок,
скрипт приходит томом и значений не содержит. В строке команды пароля нет. На стенде и в бою
новый пароль приходит через файл окружения и пересоздание db (Rollout); оракул, когда меняет
пароль на лету, передаёт `exec -e ИМЯ` без значения — compose берёт его из окружения вызывающего.

**Почему не миграция.**
- Роль миграций не может завести сама себя: первой ревизии пришлось бы войти суперпользователем,
  и адрес суперпользователя был бы у migrate.
- migrate узнал бы пароль роли сервиса — чужой секрет процесса, о котором правило
  `foreign-secret` Ч1.5а.
- Роли общие на весь кластер, а история alembic — у каждой базы своя. `downgrade` снимал бы
  роли, нужные другой базе того же кластера, а тесты двух сессий на общем кластере разработки
  делили бы имена ролей.
- Команда с паролем шла бы через движок сервиса: `DB_ECHO_SQL` напечатал бы её в журнал.

**Почему не только выкат.** Выката нет до Ч1.6, а роли нужны стеку сейчас — оракулу и джобе
`stack`. Без пути «пустой том» `docker compose up` на новом сервере поднимал бы базу без ролей до
первого шага выката. Выкат — вызывающий того же файла, а не его хозяин.

**Почему не отдельный разовый сервис compose** — в «Rejected alternatives», вторая запись.

## Approach

Срез 0 — пробы до кода, затем пять срезов кода: «Учётки-1» — срезы 0–2, «Учётки-2» — срезы 3–5
(`split.md`). Срез 1 делится между ними, пробы redis — в начале «Учёток-2». Контрольные точки —
после коммита среза 1 и после коммитов срезов 3 и 4.
Каждый срез кода — отдельные коммиты; тест или шаг оракула сначала красный, потом зелёный.
Порядок: проверка старта и образец — без Docker, первыми. Правила compose — после своих правок
compose: шаг A73 судит настоящий файл, и правило, вставшее раньше compose, держало бы его

## Stack / boundaries
- **Новых пакетов и образов нет.** psql 16 — из образа postgres Ч1.5а: `\getenv` есть с psql 15,
  `\gexec`, `\if` и `:{?имя}` — давно. redis-cli, `REDISCLI_AUTH` и `redis-server -` — из образа
  redis 7.4 Ч1.5а; пользователь `redis` — тоже из него.
- **Граница:**
  - `config` от `ops` не зависит; правила читают таблицу ролей и список процесса из `config`,
    а не держат свои копии. Ключ замка из `storage.locks` читает тест A179, а не правила:
    зависимости `ops` от `storage` нет, как в Ч1.5а;
  - скрипт ролей — вне пакета и вне образа сервиса: его исполняет psql в контейнере db;
  - проба базы — вне пакета: оракул подаёт её в `python -` внутри контейнера процесса;
  - оракул пакет не импортирует (правило Ч1.5а).
- **Гейт контура:** рисковый путь в STATUS один — `deploy/db/`; строка `artifact_oracle:` — та
  же, `scripts/stack_oracle.py` первым путём; тест таблицы шагов называет A85 и A170–A173.
- **Зависимость:** Ч1.6 зависит от обеих поставок. Боевое наложение — в main (Ч1.5в); команду
  Redis в нём и правило `redis-auth`, которое её судит, приносят «Учётки-2».

## Rejected alternatives
- **Роли — скриптом начальной настройки, а не ревизией alembic.** Выбрал скрипт вместо
  миграции, потому что роль миграций не заведёт сама себя, migrate узнал бы пароль роли
  сервиса, роли общие на кластер, а история alembic — у каждой базы своя, и команду с паролем
  напечатал бы `DB_ECHO_SQL`; цена — на поднятом томе образ скрипт не запускает: нужна вторая
  команда через `exec` (README, Ч1.6) и строки A170, около 75 строк оракула.
- **Без разового сервиса compose для ролей.** Выбрал файл в `/docker-entrypoint-initdb.d/` и
  `exec` вместо сервиса `db-roles` на образе postgres, который входил бы суперпользователем по
  TCP на каждом `up`, потому что шестой сервис несёт пароль суперпользователя ещё в один
  контейнер, а правила `order`, `restart`, `init` и права Ч1.5а–Ч1.5б пришлось бы
  распространять на него; цена — на поднятом томе роли сами не обновляются: команда скрипта —
  одна строка в скрипте выката Ч1.6 на каждом выкате.
- **Адреса — целиком в переменных сервера, а не собраны compose из пароля.** Выбрал
  `MIGRATE_DATABASE_URL`, `API_DATABASE_URL` и `API_REDIS_URL` целиком вместо
  `postgresql+asyncpg://audit_app:${POSTGRES_APP_PASSWORD:?…}@db:5432/audit`, потому что правило
  `secret-form` Ч1.5а требует значение целиком `${VAR:?}`, A67 Ч1.5а нужен неверный пароль только
  у migrate, а сырой пароль внутри адреса ломается на `%` и `@`; цена — три пароля записаны в
  файле окружения сервера дважды; расхождение громкое (`28P01`), у очереди — с Ч1.8; сверка до
  `up -d` — Ч1.6.
- **Пароль Redis — в настройках со входа, а не аргументом и не подстановкой compose.** Выбрал
  `sh -c` с `exec redis-server - <<EOF` и строкой `requirepass $$REDIS_PASSWORD` вместо
  `--requirepass` аргументом и вместо `["redis-server", "--requirepass", "${REDIS_PASSWORD}"]`,
  потому что аргумент виден в строке процесса, пока Redis её не переписал, а подстановка
  compose кладёт значение в `Config.Cmd`, в `docker ps --no-trunc` и в вывод
  `docker compose ps` — а с ними в журнал выката и открытой джобы; цена — команда redis в
  `docker-compose.yml` и в наложении — многострочная строка, а не список: правила `redis-auth`
  и `redis-memory` разбирают строку.
- **Вход, а не файл настроек в `tmpfs`.** Выбрал настройки со входа вместо файла с
  `requirepass`, который `sh -c` пишет в `tmpfs` при старте, потому что файл — ещё одна копия
  пароля в контейнере, а у входа файла нет: вход главного процесса — канал, в `/tmp` пусто
  (проба 12:24Z); цена — Redis читает настройки только на старте: смена пароля — пересоздание
  контейнера, как у любой правки окружения.
- **Точка входа без `user:`, а не `user: redis` по имени.** Отвергнута решением проверяющего
  2026-11-19T12:44Z — его прежнее решение 12:26Z снято пробой h3, — потому что под
  `cap_drop: [ALL]` Ч1.5б точка входа не стартует: `setpriv: setresuid failed`, код 127 (проба
  исполнителя 12:39Z); цена — `user: redis` в `docker-compose.yml` ставит эта поставка, и его
  держит правило `redis-auth`.
- **Точка входа вместе с `user: redis`.** Отвергнута, потому что при не-root точка входа ничего
  не делает — лишнее звено (вариант h2 пробы: тот же итог, что h1); цена — нет, кроме длины
  команды.
- **`user:` числами, `999:1000`.** Отвергнут, потому что числа uid и gid внутри образа разные у
  alpine и debian, а имя `redis` у них общее; цена — имя разрешает сам образ: смена
  пользователя в образе redis — правка правила `redis-auth`.
- **Проверка здоровья — `REDISCLI_AUTH` и сверка с `PONG`, а не `redis-cli -a`.** Выбрал
  переменную окружения вместо аргумента, потому что аргумент каждые 5 с виден в списке
  процессов общего сервера; сверка ответа — потому что без `-e` redis-cli выходит с кодом 0 и на
  `NOAUTH`; цена — проверка здоровья redis в `docker-compose.yml` — `CMD-SHELL` с конвейером
  `| grep -x PONG`; случай проверки здоровья в правиле `redis-auth`.
- **Один пароль Redis у пользователя `default`, а не ACL по процессам.** Выбрал `requirepass`
  вместо файла ACL, потому что до Части 3 у очереди один клиент, а файл ACL — ещё один файл с
  хешами паролей на сервере; цена — у api все команды `default`, включая `FLUSHALL` и снятие
  пароля `CONFIG SET requirepass`; пароль один — в `REDIS_PASSWORD` и `API_REDIS_URL`; ACL — с
  воркером.
- **Роль миграций — владелец базы, а не только `CREATE` на `public`.** Выбрал
  `ALTER DATABASE … OWNER TO audit_migrate` вместо `GRANT CREATE ON SCHEMA public`, потому что
  доверенные расширения и новые схемы будущих ревизий требуют `CREATE` на базу; цена — роль
  миграций может удалить базу `audit` целиком, как и все свои таблицы; это одна строка
  `roles.sql`.
- **Права сервиса — четыре на таблицы и два на последовательности, а не `ALL`.** Выбрал
  `SELECT, INSERT, UPDATE, DELETE` и `USAGE, SELECT` вместо `GRANT ALL`, потому что `TRUNCATE`
  стирает таблицу мимо построчных правил, а `REFERENCES` и `TRIGGER` сервису не нужны; цена —
  функции, которой понадобится `TRUNCATE`, достанется `42501`: право — одна строка `GRANT` в
  `roles.sql` и строка A85.
- **Отзыв лишнего перед выдачей, а не одна выдача.** Выбрал в скрипте `REVOKE ALL` у роли сервиса
  и снятие членств перед выдачей вместо одной выдачи, потому что скрипт идёт на каждом выкате и
  после восстановления, и ошибочная выдача иначе переживала бы исправленный скрипт; цена —
  около 10 строк `roles.sql` и строка A170, около 14 строк оракула; ручная выдача роли сервиса
  сверх скрипта снимается следующим выкатом.
- **Замок миграций в скрипте, а не запуск без замка.** Выбрал `pg_advisory_xact_lock(1001)`
  вместо скрипта без замка, потому что без него второй запуск падает на гонке заведения роли, а
  скрипт и migrate идут разом; цена — ключ записан числом и в `roles.sql`, и в
  `storage/locks.py`; их равенство держит A179.
- **Роли процессов — таблицей в `startup_checks`, а не настройками.** Выбрал постоянные имена
  `audit_migrate` и `audit_app` вместо настроек `DB_MIGRATE_ROLE` и `DB_APP_ROLE`, потому что
  каждая настройка — поверхность, а скрипт ролей обязан знать те же имена; цена — переименование
  роли — правка `startup_checks.py` и `roles.sql`; их равенство держит A179.
- **Права проверяет оракул, а не pytest на общей базе разработки.** Выбрал шаги в стеке вместо
  тестов на кластере `ai-geo-audit-dev`, потому что роли общие на кластер, и две сессии делили бы
  имена ролей; цена — права видны только там, где есть Docker: на машине и в джобе `stack`; шаг с
  контейнером — около 15 строк против 4–6 у теста.
- **Длину пароля роли скрипт не меряет.** Выбрал проверку длины только у процесса вместо второй
  проверки в SQL, потому что тот же пароль стоит в адресе процесса и его уже меряет A21 Ч1.2в;
  цена — короткий пароль роли скрипт примет, отказ придёт только на старте процесса, в
  `startup_checks._database`.

## Rollout / migration
- Ничего не выкатывается, боевой базы нет. База разработки и тестов `ai-geo-audit-dev` не
  меняется: тесты ходят её суперпользователем и заводят свои базы `audit_test_…`.
- **Стенд, поднятый до этой поставки:** база на томе с одной учёткой, migrate и api ходят
  суперпользователем, Redis без пароля. Переход на месте, данные тома базы остаются; роли — с
  «Учётками-1», пароль очереди — с «Учётками-2»:
  1. в файле окружения стенда — `POSTGRES_MIGRATE_PASSWORD`, `POSTGRES_APP_PASSWORD` и
     `REDIS_PASSWORD` (`openssl rand -hex 24`); `MIGRATE_DATABASE_URL` и `API_DATABASE_URL` — с
     ролями `audit_migrate` и `audit_app` и их паролями; `API_REDIS_URL` — с паролем очереди.
     Старый файл после этой поставки не даёт старта: migrate и api называют `DATABASE_URL` и
     нужную роль (A173, A174);
  2. `docker compose up -d db` — db пересоздаётся с новым окружением и смонтированным скриптом.
     Том на месте; сам образ скрипт не запускает — каталог данных не пуст;
  3. скрипт ролей командой из раздела «Кто и какой командой создаёт роли»: роли и пароли,
     владелец базы и схемы; `alembic_version` и прочие таблицы суперпользователя в `public` —
     роли миграций; лишнее у роли сервиса отозвано, права и права по умолчанию выданы (A170);
  4. `docker compose up -d` — redis пересоздаётся с паролем и `user: redis`; до Части 3 очередь
     пуста, данных нет. migrate входит ролью миграций; новых ревизий нет — код 0. api
     пересоздаётся с ролью сервиса и адресом очереди с паролем;
  5. проверка: api healthy; redis healthy с `PONG` в записи проверки, не от root; владельцы и
     права — запросами из README.
- **Смена пароля** — тот же путь: новый пароль в файле окружения, `up -d db`, скрипт через
  `exec`, затем `up -d` — migrate и api с новым адресом. Порядок на бою — Ч1.6.
- **Откат:**
  - прежние compose, образ и файл окружения — только вместе: прежний образ роли не сверяет, а
    новый с адресами суперпользователя не стартует. Поверх ролей прежний стек работает:
    суперпользователь меняет таблицы роли миграций так же, как свои. Роли можно оставить — они
    ничему не мешают;
  - снять роли совсем — суперпользователем через тот же `exec`: `REASSIGN OWNED BY
    audit_migrate TO` суперпользователь образа; `ALTER DATABASE audit OWNER TO` он же;
    `DROP OWNED BY audit_migrate, audit_app` — снимает их права и права по умолчанию;
    `DROP ROLE audit_migrate, audit_app`. Команда — в README;
  - Redis при откате снова без пароля и отвечает любому в сети `data`: откат — только до
    первого выката и решением ведущей.
