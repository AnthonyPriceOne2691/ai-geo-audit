## Approach

Срезы — отдельные коммиты, тест сначала красный. Подставной исполнитель — записи с раннера и из
разведки, у каждой — откуда она (ядро 6а-1).

**0. Слово владельца — до кода.** Пункты 2 и 4 раздела «Решает владелец» спеки: текст строки
«сверить» и исключение длины — `deploy/deploy.py` выйдет за предел 1150 уже на срезе 1.

**1. Вход (A187, строки 1–3).**
- `up <SHA> --backend-digest <D> --web-digest <D>`: SHA — `[0-9a-f]{40}`, дайджест —
  `sha256:` и 64 знака hex; отказ — до первой команды докера.
- Дерево: `git rev-parse HEAD` копии равен SHA, `git status --porcelain` пуст; иначе отказ с
  командой `git checkout --detach <SHA>` или с именами изменённых файлов. Дерево скрипт не
  переключает.
- `git` от root в клоне не от root отказывает «dubious ownership», код 128 (заметка третьей
  проверяющей около 15:04Z): отказ `up` называет эту причину, а не «дерево не на SHA» (L89,
  L134). Случай — подставным исполнителем: живой шаг его не ловит.
- Адрес `origin` — `git remote get-url origin`: схема `https`, хост `github.com` без порта и
  учётных данных, путь — ровно `/<владелец>/<имя>`, без `.git`, `/` в конце, запроса и якоря;
  что не так — словами, без адреса. Путь образов — `ghcr.io/<владелец>/<имя>-backend` и
  `-web`, строчными; тот же вид берёт джоба публикации 6в-5 (строка decisions).

**Внутренняя точка — после коммита кода среза 1,** число — по счёту гейта (L27, L103). Порог —
2300 минус срезы 2–3 × 13,4, около 910: **1390**. Больше — стоп: число ведущей.

**2. Образы, правила и разовый старт (A187, строки 4–5).**
- Порядок: `deploy.py check` той же функцией, что команда `check` (отказ — отказ `up`) →
  снимок соседа → `docker pull` backend и web по метке SHA, дайджест из `docker image inspect`
  против флагов → db и redis — по дайджесту из файла compose, только если их нет.
- Ответ реестра — классификация по записанным ответам с раннера, снятым до кода, а не по
  догадкам: какие тексты отказа значат «образа нет» (ждём «нет манифеста» и «доступ запрещён»;
  «не авторизован» — вывод без пробы), а нет ответа — «реестр не ответил» (заметка третьей около
  15:04Z). Без записей живой шаг покраснел бы «реестр не ответил» на несуществующем пакете.
- `docker pull` качает до сверки дайджеста: при отказе дайджеста, правил `--prod` или разового
  старта скачанные образы остаются на машине, в стек и файл сервера не попадают.
- Правила `--prod` — внутри скачанного образа backend, как шаг A89 оракула: вывод `docker
  compose config` боевого наложения — на stdin контейнера без сети. Исполнителю ядра нужен вход
  stdin данными — он же нужен канарейке 6в-4.
- Разовый старт migrate и api — `ops.config_check` (6а-2) разовым контейнером с новым образом и
  файлом сервера: образы — окружением процесса compose, файл сервера не тронут.
- Отказ любого шага — в выводе команда вернуть дерево на прежний SHA: прежний — последний выкат
  из истории (её заводит 6в-2); истории нет — строка «прежнего выката нет».
- Конец: строка «вход и образы сверены; подъёма в этой версии нет — 6в-2», код 0.

**3. Строка «сверить»** — по слову владельца: (а) причина словами — тест на каждую из четырёх
форм (L211); (б) — без кода.

**«Исполнение рисковых путей»** — живой шаг в джобе `stack` только на запросе на слияние (на main
после 6в-5 метка SHA опубликована, и случай «образа нет» там ломается), после оракула: от root,
`sudo -n python3 -I deploy/deploy.py`, только в CI (судит `GITHUB_ACTIONS`), корни — копия
клона и файл сервера (`copytree`, `env-init`, `put-secret`, как живой шаг 6а-3), снимает их
`finally`. Случаи: короткий SHA и нет дайджеста; правка в дереве и `HEAD` не на SHA; `origin`
копии — адрес ssh; метки SHA нет в реестре (запрос на слияние ничего не публикует) — отказ
«образа нет». Реестр на метку несуществующего или приватного пакета отвечает по-разному: какие
тексты `up` называет «образа нет» — по записанным ответам с раннера (срез 2); «реестр не
ответил» — свой отказ, и на нём живой шаг красный, а не зелёный. После каждого случая образы,
контейнеры и файл сервера — как до. Блок в verify-report — с номером прогона (L34).

## Rejected alternatives
- **Срез 1 подписанного плана — двумя поставками, а не одной.** Выбрал две поставки вместо
  среза целиком, потому что по худшей калибровке 6а срез — ~3150 строк, выше предела 2500
  (решение ведущей 2026-11-27). Цена — `up` 6в-1 не поднимает стек и кончается строкой «подъёма
  нет»; первый выкат ждёт все пять поставок.
- **Конец `up` 6в-1 — код 0 и строка «подъёма нет», а не отказ.** Выбрал код 0, потому что
  сверка прошла и ничего не тронуто, а отказ читался бы как сбой входа. Цена — до 6в-2 код 0 у
  `up` не значит «стек поднят»; на сервере `up` до конца 6в не запускается.
- **Правила `--prod` — внутри скачанного образа, а не из пакета копии на хосте.** Выбрал образ,
  потому что судят правила той версии, что выкатывается, и пакет на хост не ставится. Цена —
  один разовый контейнер без сети на выкат.
- **Путь образов `<имя>-backend` и `<имя>-web`, а не вложенный путь.** Выбрал плоские имена,
  потому что их одинаково понимают реестр, `docker pull` и джоба публикации 6в-5. Цена — путь
  задан и здесь, и в джобе: тест 6в-5 сверяет оба места.

## Risks
- **Записи ответов `docker` и `git`** отстают от версий на сервере — расхождение формата —
  красный тест, а не тихий пропуск (как у ядра 6а).
- **Пакеты реестра приватны** до действия владельца после первой публикации — `up` отказывает
  словами «образа нет» (общий план, Risks).
- **Docker Hub с адреса машины** — предел общий с соседом: db и redis — только если их нет.
- **Код 0 у неполного `up`** — до 6в-2; на сервер `up` идёт только после всей 6в.
- **Строка ресурсов `deploy.py check` на раннере — сверено, не сбылся** (данные третьей
  проверяющей около 15:04Z). Живой шаг 6а-3 печатает настоящий код `check`: на чистых
  значениях — 0 в 9 прогонах из 9 — шесть запросов 6а-3 (45993253242 … 46003093847),
  46004979610, 46011337918 и main 46004655724. `up` зовёт ту же функцию без особого флага — на
  раннере то же поведение.
